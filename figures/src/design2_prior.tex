% Prior work (deck, slide 3 "Prior Work"), second style (the look of the ScaleQsim paper).
% What the figure shows: one table of the existing implementations of Pauli propagation and of SectorQ.
% The rows are grouped by where the implementation runs (first column, a cell that spans its group, with a
% small pictogram): one device -> many CPU nodes -> many GPUs. For every implementation the three right
% columns give what this work adds: when terms move between processes, whether a run can hold more terms
% than the GPU memory, and how the terms are split over the processes.
%   One Device       SPD (1 GPU); PauliPropagation.jl, ppvm, Qiskit pauli-prop (1 node of CPU cores)
%   Many CPU Nodes   ORQA (terms move at every branching gate, fixed distribution function); MonoProp
%   Many GPUs        cuPauliProp distributed mode (terms move at every gate; the split is not public);
%                    SectorQ (terms move only at window boundaries, sectors kept in host memory, split
%                    chosen at run time)
% Message (one sentence): existing implementations stay on one device, run on CPUs, or move terms between
% all GPUs at every gate; SectorQ runs on many GPUs, moves terms only at window boundaries, holds more terms

% Sources of the entries: the same as deck_n04_positioning.tex (README 1.3, 2.4, 2.5, 3.2 to 3.4, 4.2;
